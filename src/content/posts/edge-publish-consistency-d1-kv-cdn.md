问题不是缓存，而是状态没有定义清楚

内容系统一旦同时使用关系数据库、键值缓存和 CDN，发布就不再是一次 UPDATE。数据库中的 status 已经变成 published，并不意味着用户此刻能读到新正文：公开快照可能尚未生成，KV 仍保存旧对象，边缘节点也可能继续命中旧响应。真正需要设计的是一套跨存储介质的状态机。

我把文章状态拆成四个可观测阶段：编辑态只保证 D1 中的源内容落盘；快照态生成只包含公开字段的不可变 JSON；索引态更新搜索文档和列表版本；可见态完成 KV 写入与 CDN purge。任何一步失败，都必须能判断当前停在哪一层，而不是笼统返回发布失败。

为什么公开快照不能在读取时临时生成

富文本正文通常还要做代码高亮、目录提取、媒体引用扫描和 HTML 安全处理。如果这些操作放在每次 GET 请求中，CPU 成本会进入热路径，而且同一篇文章在不同节点可能得到不同结果。发布时生成 publicContentJson，把昂贵转换移到写路径，读取端只消费稳定快照，才能保证低延迟与确定性。

缓存失效采用版本号而不是枚举删除

文章列表存在分页、标签和游标组合，逐个删除缓存键既昂贵又容易漏。更稳妥的方式是把逻辑版本放入 key：posts:list:v42:tag:react:cursor:20。发布完成后只递增版本，旧缓存自然失去可达性。详情缓存仍按 slug 精确删除，因为它的键空间可控。

并发发布需要什么保证

两个保存请求可能以相反顺序完成，异步 Workflow 也可能重复投递。处理函数必须以文章当前快照计算 hash，并把 hash 作为幂等依据：相同 hash 不重复建立修订、索引或缓存；任务执行前重新读取数据库，避免较旧任务覆盖较新内容。修订记录保存 title、slug、tagIds、publishedAt 与 contentJson，使恢复不是猜测，而是一次可审计的状态回放。

失败恢复比正常流程更重要

如果 R2 媒体写入成功而数据库记录失败，应立即安排对象删除；如果搜索索引更新失败，正文仍可公开，但系统必须保留可重放任务；如果 CDN purge 失败，应记录具体 URL 与响应，而不是吞掉异常。所有后台错误使用结构化 JSON，至少包含 postId、阶段、snapshotHash 和错误原因，才能在线上快速区分数据错误、资源绑定错误和外部服务错误。

最终验证不是看到一个 200

发布测试应该同时检查数据库状态、公开快照、KV hash、搜索结果和匿名访问页面。再通过重复执行、乱序任务、未来发布时间与撤回操作验证幂等性。只有这些条件同时成立，发布按钮才代表一次可靠的状态迁移，而不是把不确定性甩给后台任务。
